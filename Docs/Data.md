# Data Structures

This file describes the main data structures used throughout the pipeline and the final saved checkpoint.

The pipeline mainly uses `SimpleNamespace`, dictionaries, lists, sets and NumPy arrays.

---

## PubMed Paper

After extracting text from PubMed files, each paper is stored as a `SimpleNamespace`.

```python
SimpleNamespace(
    text="...",
    pmid="...",
    pmc="..."
)
```

### Fields

`text` – extracted and cleaned paper text

`pmid` – PubMed identifier for the paper

`pmc` – PubMed Central identifier where available

---

## Sentence + NER Annotations

After sentence splitting and NER, each sentence is stored with its paper identifiers and detected annotations.

```python
SimpleNamespace(
    text="...",
    pmid="...",
    pmc="...",
    annotations=[
        SimpleNamespace(
            text="lung cancer",
            locations=[
                SimpleNamespace(
                    offset=10,
                    length=11
                )
            ],
            infons={
                "entity_type": "...",
                "ner_confidence": 0.98
            }
        )
    ]
)
```

### Sentence Fields

`text` – sentence text

`pmid` – PMID of the source paper

`pmc` – PMC ID of the source paper

`annotations` – list of entity mentions detected by the NER model

### Annotation Fields

`text` – entity mention exactly as it appeared in the sentence

`locations` – location of the entity within the sentence

`offset` – character position where the entity begins

`length` – number of characters in the entity mention

`entity_type` – entity type predicted by the NER model

`ner_confidence` – confidence score returned by the NER model

---

## Candidate Arrays

SapBERT and N-gram candidate generation return NumPy arrays.

Default number of candidates generated by each method is 10.

```python
indices.shape == (n_entities, 10)
scores.shape == (n_entities, 10)
```

### Indices

Each value is an index into the loaded UMLS ontology.

The index is not itself the UMLS identifier.

The ontology entry at that index contains the UMLS ID.

For N-gram candidates, `-1` is used when no candidate exists for a position.

### Scores

SapBERT scores are similarity scores from SapBERT candidate retrieval.

N-gram scores are scores returned by the PISA index.

For missing N-gram candidates, the score is `-inf`.

These original scores are not directly compared during Reciprocal Rank Fusion.

---

## RRF Candidate Arrays

Reciprocal Rank Fusion combines the SapBERT and N-gram candidate rankings.

By default, the top 5 candidates are retained.

```python
rrf_indices.shape == (n_entities, 5)
rrf_scores.shape == (n_entities, 5)
```

`rrf_indices` – indices of the selected UMLS concepts in the ontology

`rrf_scores` – fused Reciprocal Rank Fusion scores

RRF scores are based on candidate rank and the configured SapBERT and N-gram weights.

---

## Candidate Lookup

Before preparing text for the BERT reranker, the RRF candidates are converted into a lookup.

The dictionary key is the original entity mention text.

```python
{
    "lung cancer": [
        {
            "idx": 1234,
            "id": "C0242379",
            "name": "Lung Neoplasms",
            "score": 100.0,
            "text": "[ENTITY]Lung Neoplasms[TYPES]Disease or Syndrome[SCORE]100"
        },
        ...
    ]
}
```

### Fields

`idx` – index of the concept in the loaded ontology

`id` – UMLS concept identifier from the ontology, normally a UMLS CUI

`name` – preferred name of the UMLS concept

`score` – RRF score normalised relative to the highest scoring candidate for that entity and converted to a 0–100 scale

`text` – formatted candidate information passed into the BERT reranker

Multiple candidates are stored for each entity mention.

By default there are 5 candidates after RRF.

---

## Prepared BERT Reranker Instance

Texts passed to the reranker are stored as dictionaries.

```python
{
    "text": "...",
    "candidates": [...],
    "sentence": sentence,
    "annotations": [...]
}
```

### Fields

`text` – prepared text containing sentence context, `[E]` annotation tags and candidate information

`candidates` – metadata describing the candidates represented by `[ENTITY]` tags

`sentence` – original sentence `SimpleNamespace`

`annotations` – annotations represented in this reranker instance

A sentence may create more than one reranker instance if it would otherwise exceed the token limit.

---

## Candidate Metadata

Each candidate represented in a reranker instance stores:

```python
{
    "id": "C0242379",
    "name": "Lung Neoplasms",
    "start": 120,
    "end": 128
}
```

`id` – UMLS concept ID

`name` – preferred UMLS concept name

`start` – character position of the `[ENTITY]` tag in the prepared reranker text

`end` – end position of the `[ENTITY]` tag

These coordinates are used to match BERT token-classification predictions back to candidates.

---

## BERT Reranker Scores

After prediction, each candidate has a score record.

```python
{
    "correct_score": 0.94,
    "ranking_logit": 2.75,
    "id": "C0242379",
    "name": "Lung Neoplasms"
}
```

### Fields

`correct_score` – probability that the candidate is correct

If the reranker predicts `CORRECT`, the model probability is used directly.

If the reranker predicts `INCORRECT`, the equivalent correct probability is calculated using:

```python
1 - predicted_score
```

`ranking_logit` – logit transformation of `correct_score`

`id` – UMLS concept ID

`name` – preferred UMLS concept name

The final candidate is chosen using the highest `correct_score`.

The logit is currently stored during scoring but is not used by `highest_score_per_anno`.

---

## Linked Annotations

After the BERT reranker chooses the best candidate, results are stored in a dictionary grouped by the preferred UMLS concept name.

```python
{
    "Lung Neoplasms": [
        {
            "instance_name": "lung cancer",
            "sentence_found_in": "The patient was diagnosed with lung cancer.",
            "pmid": "...",
            "pmc": "...",
            "reference_id": "C0242379",
            "reranker_confidence": 0.94,
            "ner_confidence": 0.98
        },
        ...
    ]
}
```

### Dictionary Key

The key is the preferred name of the selected UMLS concept.

For example:

```python
"Lung Neoplasms"
```

The key is currently the concept name rather than the UMLS CUI.

The UMLS identifier is stored separately in `reference_id`.

### Linked Annotation Fields

`instance_name` – observed entity mention from the original paper

This is effectively the observed synonym.

For example:

```python
"lung cancer"
"pulmonary cancer"
"lung neoplasm"
```

`sentence_found_in` – sentence containing the observed mention

`pmid` – PMID of the source paper

`pmc` – PMC ID of the source paper

`reference_id` – selected UMLS concept identifier

`reranker_confidence` – BERT reranker confidence for the selected candidate

`ner_confidence` – confidence from the NER model when detecting the original mention

---

## Confidence Scores

Two main confidence values are retained in the final linked output.

### NER Confidence

`ner_confidence` describes how confident the NER model was that the text span represented an entity.

Higher values indicate greater confidence from the NER stage.

### Reranker Confidence

`reranker_confidence` describes how confident the BERT reranker was that the chosen UMLS candidate was correct.

This is the candidate's `correct_score`.

Higher values indicate greater confidence in the entity-linking decision.

The two scores measure different stages and should not be treated as the same confidence value.

---

## Synonym Occurrences

The current pipeline does not store a separate pre-calculated occurrence counter.

Instead, every linked occurrence is stored as an individual entry in `linked_annotations`.

For a given UMLS concept, synonym frequencies can be calculated by counting `instance_name`.

Example:

```python
from collections import Counter

counts = Counter(
    annotation["instance_name"]
    for annotation in linked_annotations["Lung Neoplasms"]
)
```

This could produce:

```python
{
    "lung cancer": 1532,
    "pulmonary cancer": 84,
    "lung neoplasm": 51
}
```

Because individual occurrences are retained, confidence values and source information remain available for later reporting.

---

## Duplicate Handling

Several types of duplication are handled at different stages.

### Candidate Generation

N-gram retrieval may return multiple aliases belonging to the same UMLS concept.

These are deduplicated by UMLS concept before the top candidates are returned.

### Reranker Text Splitting

A single annotation may appear in more than one prepared reranker chunk when token-limit handling is required.

`build_linked_annotations` checks adjacent annotation contexts and avoids adding the same annotation more than once.

### Papers

Processed papers are tracked using PMID and PMC sets.

This prevents papers that have already been processed from being processed again when the pipeline is resumed.

## Pipeline Checkpoint

The full pipeline state is saved to:

```text
Data/Output/pipeline_state.pkl
```

The file is a Python pickle containing a dictionary.

```python
{
    "linked_annotations": {
        "Lung Neoplasms": [
            {
                "instance_name": "lung cancer",
                "sentence_found_in": "...",
                "pmid": "...",
                "pmc": "...",
                "reference_id": "C0242379",
                "reranker_confidence": 0.94,
                "ner_confidence": 0.98
            }
        ]
    },

    "completed_archives": {...},

    "seen_pmids": {...},

    "seen_pmcs": {...}
}
```

---

## Checkpoint Fields

### `linked_annotations`

Dictionary containing all successfully linked annotations processed so far.

The dictionary is handled as a `defaultdict(list)` while the pipeline is running.

New batches are merged into the existing dictionary rather than replacing earlier results.

### `completed_archives`

Set containing PubMed archive files that have been completely processed.

This allows the pipeline to skip entire completed archives when restarted.

### `seen_pmids`

Set containing PMIDs that have already been processed.

Used to prevent duplicate processing and to resume the pipeline safely.

### `seen_pmcs`

Set containing PMC IDs that have already been processed.

This provides an additional identifier for determining whether a paper has previously been processed.

---

## Resuming Processing

When the pipeline starts, `load_pipeline_state()` checks whether the checkpoint exists.

If no checkpoint exists, the following empty state is created:

```python
{
    "linked_annotations": defaultdict(list),
    "completed_archives": set(),
    "seen_pmids": set(),
    "seen_pmcs": set()
}
```

If a checkpoint exists, it is loaded and processing can continue using the stored state.

The following information is therefore required to resume processing:

- `linked_annotations`
- `completed_archives`
- `seen_pmids`
- `seen_pmcs`

The checkpoint should normally be kept together with the pipeline if processing is incomplete.

---

## Checkpoint Saving

The checkpoint is first written to:

```text
Data/Output/pipeline_state.tmp
```

Once writing completes successfully, the temporary file replaces the existing `pipeline_state.pkl`.

This reduces the risk of destroying the previous checkpoint if the program stops while the new checkpoint is being written.

---

## Note

When using the data for synonym analysis, `reference_id` should be treated as the UMLS concept identifier and `instance_name` as the observed synonym.
